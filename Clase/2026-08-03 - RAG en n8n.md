Esta es **la primera sesión registrada del bootcamp** en el índice de sesiones, así que no damos por visto ningún contenido previo: todo lo que los videos asumen se trata acá como gap explícito y no como "ya lo vieron en otra clase".

La sesión recorre el **pipeline completo de RAG implementado en n8n**, siguiendo una serie de cuatro videos del canal Ryan & Matt Data Science que están diseñados como secuencia (el video 2 cita al 1 en `00:22`, y el 4 reutiliza el dataset y el flujo de los anteriores). El enfoque es de implementación, no de teoría: cada video arma el flujo nodo por nodo y verifica el resultado directamente en el dashboard de Pinecone.

El recorrido es: **chunking** (cómo partir el documento sin romper el sentido), **embeddings** (cómo convertir cada chunk en un vector y guardarlo en Pinecone), **retrieval + reranking** (cómo recuperar de más y filtrar con Cohere para no ensuciar la context window) y **metadata** (cómo enriquecer cada chunk para poder filtrar, no solo buscar por similitud).

¿Por qué importa para el rol de AI Engineer? Porque RAG es el patrón por defecto para meterle conocimiento propio a un LLM, y porque las decisiones que se toman en este pipeline (chunk size, modelo de embedding, Top K, qué metadata guardás) son exactamente las que separan un demo que funciona con un PDF de juguete de un sistema que responde bien sobre documentos reales. Además, la sesión modela una práctica muy propia del oficio: usar un LLM como asistente para las partes tediosas, como escribir las Regex del ejemplo 3.

## 3. Conceptos clave / glosario

| Término | Definición | Analogía |
|---|---|---|
| **RAG (Retrieval-Augmented Generation)** | Patrón en el que, ante una pregunta, primero se **recupera** contenido relevante de una base propia y se **inyecta en el prompt** como contexto, y recién ahí el LLM genera la respuesta. Resuelve el acceso a conocimiento privado o posterior al cutoff del modelo y reduce alucinaciones. ⚠️ Ningún recurso de la sesión define esto: es un gap declarado. | Un examen a libro abierto: el modelo no tiene que saberlo de memoria, le pasás las páginas relevantes antes de que conteste. |
| **Chunking** | Partir un documento en fragmentos más chicos para no alimentar al LLM con el documento entero (video 1, `00:06`). | Cortar un libro en fichas: buscás la ficha que sirve, no cargás el libro entero. |
| **Chunk overlap** | Cantidad de texto que se repite entre el final de un chunk y el principio del siguiente, para no perder contexto en el corte (video 1, `02:49`). El preset Simple usa 200 sobre 1000 = **20%**. | La solapa de una hoja fotocopiada: repetís las últimas líneas para que la frase no quede cortada al medio. |
| **Token** | Unidad en la que los modelos miden el texto. Regla aproximada del video 1 (`17:36`): **~1 token ≈ 4 caracteres** en inglés, **100 tokens ≈ 75 palabras**. | — |
| **BPE (Byte Pair Encoding)** | Algoritmo de tokenización que usa el Token Splitter: convierte texto a tokens, corta, y vuelve a convertir a texto. | — |
| **Vector embedding** | Representación numérica del texto donde lo semánticamente parecido queda numéricamente cerca (video 2, `00:05`). | Un mapa donde los artistas musicales parecidos quedan uno al lado del otro (la analogía del propio video). |
| **Dimensiones** | Largo del vector que devuelve el modelo. `text-embedding-3-large` = **3072**, `text-embedding-3-small` = **1536**. Más dimensiones = más precisión y más costo de storage. | La resolución de una foto: más píxeles, más detalle, más peso. |
| **Vector store / vector database** | Base de datos especializada en guardar vectores y buscar por similitud. Acá se usa Pinecone. ⚠️ Gap declarado: ningún recurso explica por qué hace falta una base especializada ni qué es una búsqueda ANN. | — |
| **Índice de Pinecone** | Contenedor de vectores atado a una **dimensionalidad fija** y a una métrica de similitud. Si no coincide con el modelo de embedding, el nodo falla con *dimension mismatch*. | — |
| **Namespace** | Segregación de datos **dentro** de un mismo índice de Pinecone. Alternativa liviana a crear un índice por dataset. | Carpetas dentro de un mismo disco. |
| **Similitud coseno (`cosine`)** | Métrica de similitud que se elige en todos los demos como `metric` del índice. ⚠️ Gap declarado: ningún recurso explica qué mide ni por qué no se usa euclídea o dot product. [Completar por el profesor: explicación de similitud coseno.] | — |
| **Top K / Limit** | Cuántos chunks se recuperan del vector store en una consulta. El patrón del video 3 usa **20**. | — |
| **Reranker** | Modelo que reordena los documentos recuperados por relevancia respecto de la query (video 3, `06:00`). Es un **cross-encoder**: lee la query y el documento juntos, a diferencia del embedding (bi-encoder), que los codifica por separado. | Un editor que lee las 20 notas que trajo el redactor y elige las 4 que realmente responden a la pregunta. |
| **Relevance score** | Puntaje de 0 a 1 que devuelve el reranker (video 3, `13:01`). En el ejemplo: el chunk con la respuesta exacta puntúa **0.78**, los irrelevantes **~0.48**. | — |
| **Context window** | Cuánto texto le entra al LLM de una. Es la razón entera del chunking y del reranking. ⚠️ Gap declarado: ningún recurso lo define. | — |
| **Metadata** | Información adicional adjunta a cada chunk (autor, fechas, resúmenes, categorías) que después habilita el **filtrado** en el retrieval (video 4, `01:16`). | Las etiquetas del lomo de una carpeta: te dejan descartar estantes enteros antes de leer. |
| **Metadata explícita vs inferida** | Explícita: está literalmente en el documento y se extrae (Regex, parsing). Inferida: la produce un LLM leyendo el contenido (título, resumen, keywords). | — |
| **Structured Output Parser** | Sub-nodo que fuerza al LLM a devolver un JSON con un schema definido, para poder usar la salida como metadata. ⚠️ Gap declarado: el video 4 lo usa en `10:00` sin explicarlo. | — |
| **Sub-node vs root node** | En n8n, los root nodes procesan items secuencialmente; en los **sub-nodos las expresiones resuelven solo al primer item**. Los splitters, embeddings y el reranker son sub-nodos; el Pinecone Vector Store es root node. | — |
| **Trial Key vs Production Key (Cohere)** | Trial: fuertemente rate-limited y **no permitida para uso comercial**. Production (pay-as-you-go): ~100x más throughput. | — |

### 1. Ingesta y chunking

**La idea.** Un LLM no se come el documento entero: le pasás **N chunks** relevantes. Por eso el primer paso del pipeline es partir el documento. Y es un paso que **no se arregla aguas abajo**: si chunkeaste mal, ningún embedding ni reranker te salva. El video 1 lo justifica en `00:14`: se alimenta al LLM con N chunks en vez del documento entero para no reventar la context window.

**Los modos que muestra el video 1 (25:47):**

| Modo | Cómo corta | Cuándo usarlo |
|---|---|---|
| **Simple** (preset del Default Data Loader) | 1000 caracteres / 200 de overlap | Default rápido |
| **Character Text Splitter** | Por un **separador explícito** (ej. el punto) | Documentos con estructura predecible y marcada: CSV-like, logs, transcripciones línea por línea |
| **Token Splitter** | Por **tokens BPE** | Cuando querés controlar el costo/límite real del modelo, que se mide en tokens |
| **Recursive Character Text Splitter** | Jerarquía de separadores: párrafo → oración → palabra, "manteniendo juntos" tanto como se pueda | **El recomendado por default** (`19:30`) |

> ⚠️ **Corrección al video (verificada en la doc oficial).** El video presenta "cuatro splitters", pero **el modo Simple no es un algoritmo distinto**: es el **Recursive Character Text Splitter con chunk size 1000 y overlap 200**. O sea: hay **tres nodos de splitter + un preset**. No pienses en el Simple como un algoritmo naïve inferior; es el algoritmo recomendado con valores por defecto.

**Caracteres vs tokens.** El video lo trabaja en `17:36` con la regla ~1 token ≈ 4 caracteres en inglés y 100 tokens ≈ 75 palabras. La forma más rápida de internalizarlo es jugar con el [OpenAI Tokenizer](https://platform.openai.com/tokenizer), que el video usa en vivo en `17:09`. Esa misma herramienta te sirve después para estimar **costo de embeddings**, que se cobra por token.

**Ejemplo de configuración (Default Data Loader):**

```
Type of Data:   Binary  (o JSON según la fuente)
Text Splitting: Simple  →  Recursive Character Splitter, chunk 1000 / overlap 200
                Custom  →  conectás el sub-nodo de splitter que quieras
```

```
Recursive Character Text Splitter → Chunk Size (caracteres) + Chunk Overlap     ← recomendado por default
Character Text Splitter           → Chunk Size + Chunk Overlap + separador      ← docs con separador explícito
Token Splitter                    → Chunk Size (en TOKENS BPE) + Chunk Overlap  ← ojo, ver gotcha
```

**Gotchas**

- ⚠️ **Inconsistencia en la doc de n8n del Token Splitter:** la descripción del nodo habla de tokens BPE, pero el help text del parámetro dice *"Chunk Size: number of characters"*. Es un error de la propia documentación. **El video es el que está bien: en ese nodo el chunk size se cuenta en tokens** (por eso lo pone en 500 tokens en `16:30`).
- ⚠️ **El Recursive de n8n no expone separadores custom.** Solo Chunk Size y Chunk Overlap. Si venís de LangChain, donde sí podés pasar la lista de separadores, esto te va a sorprender.
- ⚠️ **En sub-nodos, las expresiones resuelven solo al primer item** (a diferencia de los root nodes, que procesan items secuencialmente). Está advertido en la doc de todos los sub-nodos.
- El chunk size del Character Splitter es un **límite superior, no un corte exacto**: se acerca al límite pero respeta el separador.
- El blog companion **no publica el JSON del workflow ni el dataset** (están detrás de la comunidad de pago del canal): vas a tener que armar el flujo a mano.

### 2. Vectorización y almacenamiento

**La idea.** Un **embedding** convierte texto en un vector: lo semánticamente parecido queda numéricamente cerca. La intuición central del video 2 (`02:30`): *"las cosas que están estrechamente relacionadas van a tener representaciones numéricas muy cercanas"*. Esos vectores se guardan en un índice de Pinecone, y cuando consultás, tu pregunta también se convierte a vector y se busca lo más cercano.

**Los dos modelos de OpenAI que usa el video, y sus números verificados al 2026-08-11:**

| Modelo | Dimensiones | Input máximo | Costo / 1M tokens |
|---|---|---|---|
| `text-embedding-3-small` | **1536** | 8192 tokens | **US$ 0.02** |
| `text-embedding-3-large` | **3072** | 8192 tokens | **US$ 0.13** |
| `text-embedding-ada-002` (legacy) | 1536 | 8192 tokens | US$ 0.10 |

> ⚠️ **Corrección al video.** En `07:07` se dice que `3-large` es *"un poquito más caro"* que `3-small`. **Falso**: es **6.5x más caro** (0.13 vs 0.02). Con Batch API: 0.065 vs 0.01. La ganancia de precisión es real, pero el trade-off de costo es mucho más agresivo de lo que sugiere el video.

> 💡 Sobre `ada-002`: el video recomienda no usarlo (`01:12`). Es una **opinión, pero bien fundada**. La doc de OpenAI **no lo marca como deprecated** y sigue disponible, pero a US$0.10/1M es **5x más caro que `3-small`** y de peor calidad — de hecho, `3-large` truncado a 256 dimensiones ya supera a `ada-002` a 1536. El argumento económico es más fuerte que el que da el video.

**La regla dura de RAG (video 2, `03:24`):**

> ⚠️ *"Cuando hacés query, así como cuando hacés embed, necesitás usar exactamente el mismo modelo."*
> Si no, el retrieval devuelve basura, o directamente falla por **dimension mismatch**. Es el error #1 de los principiantes en RAG.

**Configuración del nodo Embeddings OpenAI:**

```
Model:           text-embedding-3-small | text-embedding-3-large
Base URL:        (opcional) endpoint OpenAI-compatible self-hosted
Batch Size:      máximo de documentos por request
Strip New Lines: on/off
Timeout:         segundos ( -1 = sin timeout )
```

- **Batch Size** impacta rate limits y velocidad de ingesta.
- **Base URL** es el escape hatch: te deja apuntar a embeddings locales o self-hosted (Ollama, LM Studio, Infinity) **sin cambiar el resto del pipeline**. Muy relevante si querés evitar servicios de pago.
- **Timeout** importa en ingestas largas.

**El nodo bisagra: Pinecone Vector Store.** Es el punto de encuentro de los cuatro videos — recibe los chunks del subtema 1, los embeddings del 2, dispara el reranker del 3 y guarda/filtra la metadata del 4. Si entendés este nodo, entendés la arquitectura de RAG en n8n. Sus **cinco modos**:

| Modo | Para qué |
|---|---|
| *Insert Documents* | Ingesta |
| *Get Many* | Similarity search devolviendo score. **Único modo con Metadata Filtering** |
| *Retrieve Documents (As Vector Store for Chain/Tool)* | Consulta desde una chain |
| *Retrieve Documents (As Tool for AI Agent)* | Consulta desde un AI Agent |
| *Update Documents* | Actualización (ningún video lo cubre) |

Parámetros clave: **Pinecone Index** (obligatorio en todos los modos), **Limit / Top K**, **Namespace**, **Name & Description** en modo tool (*"a good, specific description allows LLMs to produce expected results more often"*), **Metadata Filtering** (funciona como **AND** de todos los filtros) y el toggle **Rerank Results**.

**Gotchas**

- ⚠️ **La dimensión del índice se define al crearlo y NO se puede cambiar después.** Si querés probar los dos modelos, necesitás **dos índices**.
- ⚠️ **Límite de 8192 tokens de input** en los modelos de embedding. Esto **ata el subtema 2 de vuelta al 1**: no podés hacer chunks arbitrariamente grandes. El video no lo menciona; sale de la doc de OpenAI.
- ⚠️ **El parámetro `dimensions`** (que permite acortar el embedding sin perder sus propiedades semánticas — un `3-large` truncado a 256 supera a un `ada-002` de 1536) existe en la **API de OpenAI**, pero la doc del nodo de n8n **no lo lista**. **Inferencia de la ficha: probablemente no esté disponible desde n8n.** [Completar por el profesor: confirmar abriendo el nodo en la versión de n8n del bootcamp.]
- ⚠️ **Metadata Filtering solo existe en modo Get Many.** Importante para el subtema 4, que guarda metadata pero no muestra el filtrado en el modo agente.
- 💡 **Namespaces** son una alternativa liviana a crear un índice por dataset. Los videos no los usan.
- **Gap del video 2:** los system prompts del AI Agent se omiten o pasan muy rápido, así que la parte del agente **no es reproducible tal cual**. [Completar por el profesor: system prompt de referencia para el AI Agent.]

### 3. Retrieval y reranking

**El problema.** Si traés **pocos** chunks, te perdés la respuesta. Si traés **muchos**, ensuciás la context window y pagás de más en tokens. El video 3 plantea exactamente ese dilema y propone la salida: **recuperación en dos etapas**.

**La solución.** Recuperás de más a propósito (**Top K = 20** en Pinecone) y le pasás esos 20 al **reranker de Cohere**, que los reordena por relevancia respecto de la query y te deja los **4 mejores** para el LLM. Recall amplio primero, precisión después. La justificación core, en `01:45`: *"esto da más maneras de obtener la respuesta correcta revisando más chunks iniciales"*.

Por qué el reranker ve cosas que el embedding no: el embedding es un **bi-encoder** (codifica query y documento por separado), el reranker es un **cross-encoder** (los lee juntos). Por eso puede juzgar relevancia con más finura, aunque a costa de correr sobre pocos candidatos.

**La evidencia numérica (video 3, `13:01`):** el chunk que contiene la respuesta exacta puntúa **0.78**; los irrelevantes quedan en **~0.48**. **La separación entre esos dos números es lo que hace útil al reranker.** Los relevance scores van de 0 a 1.

**Configuración:**

```
Pinecone Vector Store
  Mode:           Retrieve as Tool for Agent
  Pinecone Index: ← el índice que creaste
  Limit / Top K:  20    ← recuperás de más a propósito
  Rerank Results: ON    ← habilita la pata hacia el sub-nodo Reranker Cohere

Reranker Cohere
  Model: rerank-v4.0-fast   ← preferí v4 si tu dropdown lo ofrece
  Top N: 4                  ← [VERIFICAR] puede no existir según la versión de n8n
```

> ⚠️ **DESACTUALIZACIÓN — el modelo de rerank.** Los videos y el soporte nativo de n8n se construyeron alrededor de **`rerank-v3.5`**. Hoy la generación vigente de Cohere es **Rerank 4.0**: `rerank-v4.0-pro` y `rerank-v4.0-fast`. En plataformas hosteadas de terceros, `cohere-rerank-3.5` fue **deprecado el 2026-07-01** y desde el **2026-08-01** las requests se sirven con `cohere-rerank-4-fast` (confirmado en la doc de Oracle OCI y en el catálogo de modelos de Pinecone; **ojo: eso es de esas plataformas, no necesariamente de la API directa de Cohere**, donde `v3.5` sigue listado).
> **Qué hacer:** mirá qué ofrece el dropdown **Model** de tu nodo y elegí `rerank-v4.0-fast` si está disponible.

> ⚠️ **Para documentos en español:** sirven `rerank-multilingual`, `v3.5` y `v4.0`. **`rerank-english-v3.0` NO.** A partir de v3.5 Cohere abandonó el esquema de modelos separados english/multilingual de la v3.0.

> ⚠️ **El parámetro Top N puede no existir en tu versión.** La doc del nodo Reranker Cohere documenta **solo Model**, no un Top N. Existe un PR abierto (`n8n-io/n8n#17921`) que lo agrega. Según la versión, el "quedate con los 4 mejores" puede setearse en el reranker **o derivarse del Top K del vector store**. [Completar por el profesor: abrir el nodo en la instancia del bootcamp antes de dar el ejercicio y confirmar dónde se setea ese número.]

**Gotchas**

- ⚠️ **Rate limits de la Trial Key de Cohere.** Trial es fuertemente rate-limited y **explícitamente no permitida para uso productivo/comercial** (confirmado en la doc oficial; el video lo afirma en `07:12`). Números de fuentes secundarias: **~1.000 llamadas/mes** y **10 requests/min en el endpoint de rerank**. Production (pay-as-you-go): **~1.000 RPM en rerank**, ~100x más throughput.
  **Consecuencia práctica para la clase: con 10 RPM, si 20 alumnos ejecutan el workflow al mismo tiempo van a comer 429s.** Escalonen la práctica.
- ⚠️ **El toggle "Rerank Results" requiere n8n ≥ 1.98.** Si tenés una instancia self-hosted vieja, directamente no lo vas a ver.

### 4. Metadata

**La idea.** La metadata es información adicional que viaja pegada a cada chunk: autor, fechas, resúmenes, categorías. Sirve para dos cosas: **filtrar** en el retrieval (Metadata Filtering, modo Get Many del nodo Pinecone) y responder preguntas del tipo *"¿qué dice el documento X de 2023?"* en vez de depender solo de similitud semántica pura.

**La regla de diseño (video 4, `02:40`):**

> 💡 *"Pensá siempre en las potenciales queries que alguien va a buscar al armar tu pipeline."*
> La metadata **se diseña hacia atrás**, desde las consultas esperadas. No guardes campos "porque sí": guardá los que vas a querer filtrar.

**Las tres estrategias, en orden de sofisticación:**

**1. Manual** (`05:00`) — campos estáticos que aplican a todo el documento, configurados en la opción de metadata del **Default Data Loader**. Es el mismo nodo del subtema 1: **cumple dos funciones distintas en esta sesión** (chunking y metadata). La doc lo confirma: permite *"set the metadata that should accompany the document in the vector store"*, y esa metadata es la que después habilita el filtrado en retrieval.

**2. Generada por IA** (`10:00`) — un LLM con un **Structured Output Parser** produce título, resumen de una oración y keywords, con JSON schema forzado.

> ⚠️ **Limitación que el propio video advierte y no resuelve:** este ejemplo **puede fallar si el documento supera la context window del LLM**, porque le manda el documento completo para resumir.

**3. Extracción dinámica** (`14:00`–`19:10`) — el caso difícil: cada chunk recibe metadata **distinta** según la subsección a la que pertenece, en un documento con estructura visual pero sin marcado estricto. La solución del video: un script Python con Regex, **generado y depurado conversando con Claude** (`16:40`), ejecutado en un **Code node** y enviado al Vector Store.

Sobre delegar las Regex en un LLM, el video dice en `14:58`: *"odio escribir expresiones regulares; una de las mejores cosas de los LLMs es que son geniales en eso"*, y afirma que un LLM te lleva al 80-90%.

> ⚠️ Ese 80-90% (`16:58`) es **una opinión presentada como dato**: no hay benchmark citado ni forma de verificarlo. Tomalo como heurística anecdótica, no como métrica.

**El script del video NO es copiable.** El código en pantalla está ilegible (`17:12`) por la velocidad de navegación. Lo único que se sabe con certeza es qué hace: importa `re` y `json`, parsea el texto, aplica expresiones regulares para fechas y grupos, y anexa metadata estructurada a cada chunk. Lo que sigue es una **reconstrucción conceptual propuesta**, no una transcripción:

```python
# RECONSTRUCCIÓN CONCEPTUAL — no es el código del video
import re, json

resultados = []
for item in _input.all():
    texto = item.json["text"]                      # ← placeholder: el campo donde viene tu chunk
    anio = re.search(r"\b(19|20)\d{2}\b", texto)   # ← placeholder: tu patrón real
    resultados.append({
        "json": {
            "text": texto,
            "metadata": {"year": anio.group(0) if anio else "Unknown"},
        }
    })
return resultados
```

> 💡 El `"Unknown"` no es decorativo: en `19:10` el video muestra que **algunos chunks detectan el año y otros no**, y que **eso es un resultado aceptable, no un bug**.

**Gotchas**

- ⚠️ **Metadata Filtering solo funciona en modo Get Many** del nodo Pinecone, y actúa como **AND** de todos los filtros. El video 4 guarda metadata pero no muestra el filtrado en el modo agente.
- ⚠️ El video 4 usa **Regex** y **Structured Output Parser** sin explicarlos. Cita un *"Regex Cheat Sheet"* en `15:11` **sin URL**, así que no es identificable. [Completar por el profesor: elegir una referencia de Regex propia si querés que el Ejemplo 3 sea reproducible sin depender del LLM.]
- [Completar por el profesor: si querés que el Ejemplo 3 sea evaluable, hace falta un script de referencia propio, porque el del video no se puede transcribir.]

### 5. Cómo se conecta todo (relaciones a tener en la cabeza)

- **El Default Data Loader aparece en el video 1 y en el 4 con funciones distintas** (chunking y metadata). Es **el mismo nodo**: no son dos cosas.
- **El Pinecone Vector Store es el punto de encuentro de los cuatro videos.** Todo lo demás son sub-nodos que se le cuelgan.
- **El video 3 depende del 1 y del 2:** el reranker opera sobre chunks (video 1) recuperados por similitud vectorial (video 2). Sin eso, no tiene sobre qué operar.
- **El video 4 depende del nodo Pinecone del video 2** para el filtrado por metadata, y su Ejemplo 3 reutiliza el splitter recursivo del video 1.
- **Video 3 y video 4 son complementarios, no alternativos:** el reranker mejora el **orden** de lo recuperado; la metadata mejora **qué** se recupera (filtrado). Un pipeline maduro usa los dos.
- **El límite de 8192 tokens de input del embedding ata el subtema 2 de vuelta al 1:** no podés hacer chunks arbitrariamente grandes.

## 5. Guía práctica paso a paso

En esta sesión **no hay comandos de CLI**: todo se configura por la UI de n8n y por las consolas de Pinecone / OpenAI / Cohere.

### Prerequisitos

- Una instancia de n8n **≥ 1.98** (versiones anteriores no muestran el toggle *Rerank Results*).
- Cuentas en **Pinecone**, **OpenAI** y **Cohere**.
- Un documento de prueba. ⚠️ El blog companion **no publica el dataset ni el JSON del workflow** (están en la comunidad de pago del canal), así que armás el flujo a mano. [Completar por el profesor: preparar un dataset propio y, si se puede, un workflow base importable.]

### Paso 1 — Sacar las API keys

| Placeholder | Dónde se usa | Cómo obtenerlo |
|---|---|---|
| `TU_PINECONE_API_KEY` | Credencial Pinecone en n8n | Consola de Pinecone → API Keys (video 1, `03:00`) |
| `TU_OPENAI_API_KEY` | Credencial OpenAI en n8n | platform.openai.com → API Keys |
| `TU_COHERE_API_KEY` | Credencial Cohere en n8n | Dashboard de Cohere → Trial Key (video 3, `06:37`) |

**Verificación:** las tres credenciales guardadas en n8n sin error de autenticación.

### Paso 2 — Crear el índice en Pinecone (ANTES de correr el workflow)

La dimensión del índice tiene que coincidir **exactamente** con la del modelo de embedding.

| Modelo de embedding | `dimension` del índice | `metric` |
|---|---|---|
| `text-embedding-3-small` | **1536** | `cosine` |
| `text-embedding-3-large` | **3072** | `cosine` |
| `text-embedding-ada-002` (legacy) | 1536 | `cosine` |

En los videos esto se hace **por la UI de la consola de Pinecone**. El equivalente por SDK va como referencia (**no aparece en los videos**):

```python
from pinecone import Pinecone, ServerlessSpec

pc = Pinecone(api_key="TU_PINECONE_API_KEY")   # ← placeholder: tu key de Pinecone
pc.create_index(
    name="baseball-cards-large",   # ← placeholder: nombre de tu índice
    dimension=3072,                # ← 3072 para 3-large, 1536 para 3-small. NO se puede cambiar después
    metric="cosine",               # cosine es el default razonable para embeddings de texto
    spec=ServerlessSpec(cloud="aws", region="us-east-1"),  # ← placeholder: cloud/region de tu proyecto
)
```

> ⚠️ La `region` y el `cloud` disponibles dependen del plan, y las fuentes sobre el **free tier de Pinecone** al 2026 son contradictorias. Los ejercicios piden crear **al menos 2 índices** (1536 y 3072).
> [Completar por el profesor: chequear en la consola de Pinecone el día de la clase cuántos índices y vectores entran en el free tier.]

**Verificación:** el índice aparece en el dashboard de Pinecone con la dimensión correcta.

### Paso 3 — Armar la ingesta (chunking)

1. Trigger (el video 2 usa un **form trigger**) → extractor del documento.
2. **Pinecone Vector Store** en modo **Insert Documents**, apuntando a tu índice.
3. Colgale un **Default Data Loader**:
   - `Type of Data`: Binary o JSON según la fuente.
   - `Text Splitting`: **Simple** para empezar (= Recursive, 1000/200), o **Custom** si querés conectar un splitter propio.
4. Si elegiste Custom, colgá el sub-nodo de splitter:
   - **Recursive Character Text Splitter** ← el default recomendado.
   - **Character Text Splitter** si tu documento tiene separador explícito.
   - **Token Splitter** si querés medir en tokens (el video usa 500).

**Verificación:** en el dashboard de Pinecone, mirá los chunks. Con overlap configurado, **las últimas palabras de un chunk aparecen al inicio del siguiente**.

### Paso 4 — Conectar el embedding

Colgale al Vector Store el sub-nodo **Embeddings OpenAI**:

```
Model:           text-embedding-3-large   (índice de 3072)  |  text-embedding-3-small (índice de 1536)
Base URL:        (opcional)
Batch Size:      máximo de documentos por request
Strip New Lines: on/off
Timeout:         segundos ( -1 = sin timeout )
```

> ⚠️ **Regla de oro (video 2, `03:24`): el mismo modelo en ingesta y en query. Sin excepciones.**

**Verificación:** el nodo no tira *dimension mismatch* y en Pinecone aparecen vectores. El array del JSON de salida de `3-small` va del índice **0 al 1535**.

### Paso 5 — Armar la consulta con reranking

1. Segundo flujo con un **AI Agent**.
2. **Pinecone Vector Store** en modo **Retrieve Documents (As Tool for AI Agent)**, con el **mismo índice** y **el mismo nodo de embedding** que la ingesta.
3. Escribí una **Name & Description** específica para la tool — la doc lo dice explícito: *"a good, specific description allows LLMs to produce expected results more often"*.
4. `Limit / Top K` = **20**.
5. Activá el toggle **Rerank Results**.
6. Colgá el sub-nodo **Reranker Cohere** con `Model: rerank-v4.0-fast` (si tu dropdown lo ofrece; los videos usan `v3.5`) y el corte en **4** documentos.

> ⚠️ Dónde se setea ese "4" **depende de tu versión de n8n**: puede ser un `Top N` del reranker o derivarse del Top K del vector store (ver PR `n8n-io/n8n#17921`).

**Verificación:** el output del reranker devuelve exactamente **4 items**, y en el JSON los relevance scores separan claramente el chunk relevante (~0.78) de los irrelevantes (~0.48).

### Paso 6 — Agregar metadata

1. **Manual:** en el Default Data Loader, opción de metadata → agregá un campo estático (ej. `Autor`).
2. **Con LLM:** nodo de LLM + **Structured Output Parser** con el schema que quieras (ej. `keywords`, `summary`).
3. **Dinámica:** **Code node** de Python con Regex, que anexe metadata distinta por chunk, y de ahí al Vector Store.

**Verificación:** en Pinecone, todos los chunks del documento comparten la metadata manual; y en el caso dinámico, la propiedad cambia chunk a chunk (con algunos en `"Unknown"`, que es esperable).

> ⚠️ **Antes de que toda la clase ejecute a la vez:** con la Trial Key de Cohere tenés **~10 RPM en rerank**. Escalonen las ejecuciones o van a comer 429s.

## Anexo — Temas que esta sesión NO cubre

La ficha los marca como candidatos a sesiones siguientes. Te los dejamos acá para que sepas dónde están los bordes de lo que aprendiste:

1. **Evaluación de un sistema RAG** — no hay ninguna métrica más allá de "mirá si la respuesta está bien". Nada de recall@k, precision@k, faithfulness ni datasets de evaluación. Es la contracara natural de todo lo que enseña la sesión: *¿cómo sabés si tu chunking es mejor?*
2. **Cómo elegir chunk size y overlap con criterio** — los valores 1000/200 y 500 tokens se dan como recetas, sin método para tunearlos.
3. **Actualización y borrado de documentos** — el nodo Pinecone tiene modo *Update Documents* pero ningún video lo cubre. ¿Qué pasa cuando el PDF cambia? ¿Cómo evitás duplicados al re-ingestar?
4. **Hybrid search** (BM25 + vectorial) — no se menciona.
5. **Costos del pipeline completo** — nadie estima cuánto sale vectorizar N documentos ni cuánto cuesta cada query (embedding + rerank + tokens del LLM).
6. **Alternativas al stack** — todo es Pinecone + OpenAI + Cohere. No se mencionan Supabase/pgvector, Qdrant, Weaviate ni embeddings locales, pese a que el campo **Base URL** del nodo de n8n los habilita.
7. **Privacidad y datos sensibles** — mandar documentos corporativos a OpenAI + Pinecone + Cohere tiene implicancias que ningún recurso menciona.
